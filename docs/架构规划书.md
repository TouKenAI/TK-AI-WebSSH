## 1. 项目概述

### 1.1 项目定位

**TKAI SSH** = Web SSH终端 + AI Agent助手，面向纯内网环境的运维人员。

**核心价值**：让不懂命令行的人也能通过自然语言运维Linux服务器和网络设备。

### 1.2 目标用户

| 用户类型 | 痛点 | 我们的价值 |
|---------|------|-----------|
| 企业运维人员 | 不会命令行，不敢操作 | 自然语言操作，AI生成命令 |
| 网络管理员 | 设备型号多，命令不统一 | AI适配不同设备命令 |
| 企业IT主管 | 操作无审计，风险高 | 完整操作日志，可追溯 |

### 1.3 核心场景

```
用户：帮我查看服务器磁盘使用情况
AI：我将执行命令 df -h 查看磁盘使用情况，是否继续？
用户：确定
AI：执行完成。结果显示根分区使用率85%，建议清理日志文件。
```

## 2. 设计原则

### 原则 1：AI可维护（核心原则）

**为什么重要**：陈先生明确说"开发+维护都交给AI智能体来做"。

**落地实践**：

1. **代码即文档**：函数名、变量名清晰，注释解释"为什么"而不是"做什么"
2. **单一职责**：每个函数不超过50行，每个文件不超过300行
3. **显式依赖**：import语句集中放在文件头部，不用动态导入
4. **配置即代码**：所有配置用YAML/JSON，不用硬编码
5. **错误可追溯**：每个错误都有明确日志，包含上下文信息

**示例**：

```python
# ❌ 差：AI看不懂这个函数在干什么
def proc(data):
    r = requests.post(url, json=data)
    return r.json()

# ✅ 好：AI一看就懂，还能改
def send_command_to_ai(command_result):
    """
    将命令执行结果发送给AI分析
    
    Args:
        command_result: SSH命令执行结果（字符串）
    
    Returns:
        AI分析结果（字符串）
    """
    response = requests.post(
        STEPFUN_API_URL,
        headers={"Authorization": f"Bearer {STEPFUN_API_KEY}"},
        json={
            "model": "step-3.5-flash-2603",
            "messages": [{"role": "user", "content": f"分析这个结果：{command_result}"}]
        }
    )
    return response.json()["choices"][0]["message"]["content"]
```

### 原则 2：简单可靠

**为什么重要**：纯内网环境，出问题要能快速定位。

**落地实践**：

1. **少依赖**：能用标准库的就不用第三方库
2. **日志详细**：每个关键操作都写日志
3. **错误不吞**：该报错就报错，不要静默失败
4. **配置简单**：一个配置文件搞定，不要到处找

### 原则 3：分阶段验证，快速迭代

不追求一步到位，每阶段都有可演示成果，根据反馈调整。

## 4. AI架构设计

### 4.1 AI 交互模式（分阶段演进）

| 阶段 | 模式 | AI 能力 | 人做什么 |
|------|------|---------|---------|
| Phase 1 | Copilot | 生成命令 + 解释结果 | 确认每一步 |
| Phase 2 | Copilot + | 生成命令 + 解释 + 建议 | 确认危险操作 |
| Phase 3 | Semi-Agent | 自主执行安全命令 | 确认危险操作 |
| Phase 4 | Full Agent | 多步骤自主完成 | 最终确认 |

### 4.2 Phase 1：Copilot 模式（不用 function calling）

**流程**：

```
用户自然语言输入
    ↓
AI 生成 JSON 格式命令
    ↓
前端显示命令 + 描述
    ↓
用户点击"执行"
    ↓
后端执行命令
    ↓
结果返回 AI 分析
    ↓
AI 返回中文总结
```

**AI 返回格式**（Phase 1）：

```json
{
  "command": "df -h",
  "description": "查看磁盘使用情况",
  "risk_level": "safe"
}
```

### 4.3 Phase 3：Semi-Agent 模式（引入 function calling）

**流程**：

```
用户自然语言输入
    ↓
AI 调用 function calling
    ↓
后端执行命令（安全命令自动执行）
    ↓
结果返回 AI
    ↓
AI 分析，决定下一步或返回用户
```

**Function calling 定义**（Phase 3）：

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "execute_command",
        "description": "在SSH终端执行一条命令",
        "parameters": {
          "type": "object",
          "properties": {
            "command": {"type": "string", "description": "要执行的命令"}
          },
          "required": ["command"]
        }
      }
    }
  ]
}
```

### 5.2 Phase 1 实现（system prompt 注入）

```python
# 根据设备类型注入不同的 system prompt
DEVICE_PROMPTS = {
    "linux": "你是一个Linux系统运维专家。用户不懂命令行，你需要生成准确的Linux命令。",
    "huawei_vrp": "你是一个华为VRP系统运维专家。用户不懂命令行，你需要生成准确的华为VRP命令。",
    "cisco_ios": "你是一个Cisco IOS系统运维专家。用户不懂命令行，你需要生成准确的Cisco IOS命令。",
    "generic": "你是一个网络设备运维专家。请根据设备类型生成正确的命令。"
}

def get_system_prompt(device_type="linux"):
    return DEVICE_PROMPTS.get(device_type, DEVICE_PROMPTS["generic"])
```

## 6. 安全架构

### 6.1 命令安全分级

| 级别 | 定义 | 处理方式 |
|------|------|---------|
| 安全 | 查看状态（df, ls, cat） | AI 自主执行（Phase 3+） |
| 警告 | 修改配置（iptables, systemctl） | 提醒用户确认 |
| 危险 | 破坏性操作（rm -rf, mkfs） | 禁止执行，强制确认 |

### 6.2 审计日志

**记录内容**：

- 用户ID
- 目标设备IP
- 执行的命令
- 命令结果（前500字符）
- AI 分析结果
- 时间戳

**存储**：SQLite（和操作日志分开）

### 6.3 错误处理策略

| 错误场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| SSH连接失败 | 记录错误，返回友好提示 | "无法连接到服务器，请检查IP和凭证" |
| AI API调用失败 | 降级为普通SSH终端 | "AI服务暂时不可用，您可以继续使用终端" |
| 命令执行超时 | 终止命令，记录日志 | "命令执行超时，请检查命令是否正确" |
| 危险命令检测 | 拦截，要求二次确认 | "检测到危险命令，确定要执行吗？" |
| 设备类型不匹配 | 提示用户选择正确类型 | "命令执行失败，请确认设备类型是否正确" |
| AI返回格式错误 | 容错处理，使用默认格式 | "AI返回格式异常，已使用默认格式" |

### 6.4 其他安全措施

- AI API Key 通过环境变量传入（测试时可用明文，生产环境必须用环境变量）
- 终端会话加密（沿用基底的 Fernet 加密）
- 操作日志不可篡改（写入数据库 + 文件备份）
- 危险操作需要二次确认（前端弹窗）

## 7. 阶段规划

### 阶段规划排序理由

**为什么Phase 2先做Web界面增强？**

1. **客户直观感知价值** —— GUI是客户一眼能看到的差异化体验
2. **降低使用门槛** —— 图形化界面比命令行更友好
3. **建立用户信心** —— 看到监控仪表盘，用户会觉得"专业"
4. **为Phase 3打底** —— 有了好的界面，再升级AI能力更容易被接受

**为什么Phase 1不用function calling？**

- Phase 1是Copilot模式，人确认每一步，function calling没必要
- 直接返回JSON格式命令更简单，省30%代码量
- Phase 3做Semi-Agent时再引入function calling

### Phase 1：跑通 AI Copilot（~7天）

**目标**：AI 能生成命令，人确认后执行，AI 解释结果

| 任务 | 内容 | 估算 |
|------|------|------|
| T1 | Fork bifrost0x/webssh，跑通基底 | 1天 |
| T2 | 接入阶跃星辰 API（直接返回JSON） | 2天 |

- 危险命令被拦截

```yaml
database:
  url: "sqlite:///data/tkai_ssh.db"
```
